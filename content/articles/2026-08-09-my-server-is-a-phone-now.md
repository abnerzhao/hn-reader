## easy

I stopped using a small online computer (VPS) to run apps. It cost too much and slowed down when using Chrome. My phone, an old CMF model, has 8GB RAM, Wi-Fi, 5G, and a battery. I already owned it. Turning it into a server saved money and worked surprisingly well.

I used Termux, a Linux app on Android, to run services. Part of setup required rooting the phone—gaining special access. This let me install Chrome and other apps. I built systems to auto-start apps, manage power, and keep the phone running steadily.

For internet access, I used Cloudflare to hide the phone’s public address. Apps like Caddy handle websites. Surf, a browser app, connects devices like iPads.

## medium

For a while, my personal infrastructure lived on a small Hetzner VPS running a few web apps, a remote browser called Surf, and Caddy. While it worked, I disliked the cost. The cheapest shared machines struggled with heavy tasks like Chrome, and dedicated CPU machines were too expensive for a personal browser. Since DRAM prices have become astronomical, building a new server wasn't appealing either. I looked at used mini PCs but eventually remembered the CMF Phone 1 I already owned. With eight ARM cores, 8 GB of RAM, Wi-Fi 6, and a built-in battery backup, it was a perfectly capable device sitting idle in a drawer.

I initially tried to flash a normal Linux distribution directly onto the phone, but this was a mistake. I ended up with a black screen and a useless device because the Linux kernel lacked the necessary drivers for Wi-Fi, Bluetooth, and hardware acceleration. I eventually recovered the stock Android OS, which taught me a vital lesson: Android already has the drivers for everything—power management, the modem, and the GPU. Instead of replacing Android, I realized I needed a way to run Linux applications reliably while letting Android handle the hardware-specific work.

My second attempt involved using Termux as the host environment. Termux provides a Unix-like environment on top of the Android kernel, offering SSH, package management, and essential tools. To ensure stability, I used Ansible to configure an Android host profile that prevents the system from killing background processes, maintains a persistent wake lock, and keeps Tailscale active as an always-on VPN. This creates a robust recovery chain: Android boots, the VPN connects, Termux starts the supervisor, and the services launch automatically.

To run standard Linux ARM64 images, I used a combination of PRoot and chroot. PRoot is great for compatibility because it requires no root access, but it introduces overhead by intercepting system calls. For performance-heavy tasks like my Surf browser instance, I rooted the phone to use a real chroot. This allowed the applications to reach the Android kernel through native syscalls, significantly improving performance. Now, my workstation manages everything via Ansible, treating every application as an immutable artifact that can be deployed, verified, and rolled back easily.

Connectivity was the final hurdle. Since home internet lacks static IPs, I used Cloudflare Tunnels for my web apps, allowing them to reach the internet via an outbound connection without complex router rules. This also means I can move the phone between networks without losing access. For the latency-sensitive Surf browser, I wrapped the TLS stream inside a WebSocket to allow it to work through the tunnel. This setup has turned my phone into a fully functional, portable, and battery-backed server that has successfully replaced my VPS.

## hard

The initial infrastructure configuration utilized a constrained virtual private server from Hetzner, serving a modest collection of web services and a remote browsing interface. This environment, while functionally adequate, became untenable due to both economic inefficiency and operational limitations. The browser-centric application, designated Surf, imposed particular demands through its resource consumption patterns. The economy of scale achieved by shared instances proved insufficient for sustained chromium-based workloads, while purpose-built compute nodes introduced cost thresholds incompatible with personal expenditure thresholds. Physical hardware acquisition faced additional barriers through semiconductor market volatility, particularly concerning volatile memory pricing. Alternative configurations involving secondary computing devices or repurposed desktop hardware were evaluated but similarly proved impractical under current market conditions.

The identification of the CMF Phone 1 as a potential server platform emerged from its technical specifications: eight processing cores, eight gigabytes of accessible memory, and non-volatile storage capacity sufficient for application persistence. The device's integrated wireless connectivity components and power management systems presented logical advantages compared to traditional server architectures. Notably, the existing financial commitment to the device eliminated ongoing operational costs. Initial experimental deployment involved configuring the device to execute Surf alongside associated infrastructure components, demonstrating survivability across network transitions and physical relocation. This implementation required addressing fundamental incompatibilities between mobile operating system designs and conventional server environment expectations.

The first implementation strategy involved deploying a conventional Linux distribution through postmarketOS, a decision that immediately revealed fundamental architectural mismatches. The Android-derived hardware dependencies, including Wi-Fi interfaces and power management engines, remained functional through proprietary firmware but proved unusable within the Linux userspace environment. This incompatibility manifested as complete operational failure at the graphical interface stage, resulting in persistent display obsolescence. Recovery through factory image restoration necessitated navigating dual-layer firmware challenges, including transitioning between mobile and desktop operating system interfaces. The experience revealed critical insights regarding Android's hardware abstraction layer, demonstrating that Android's existing drivers provided significantly better integration with the device's SoC than alternative Linux implementations.

The operational model was subsequently redefined through Termux-based service orchestration, maintaining the Android shell while establishing a Linux-compatible host environment. This architecture preserved Android's hardware compatibility while delegating service execution to Termux's Linux userland. The infrastructure mandated specialized process management configurations to counteract Android's power optimization mechanisms. Security constraints were mitigated through Ansible-driven configuration profiles that disabled aggressive background throttling, maintained persistent wake states, and established captive VPN connectivity. The system's resilience was formalized through automated recovery sequences involving Tailscale-managed VPN reconnection and service restart protocols, enabling autonomous operation through routine reboots.

The service execution initially employed PRoot as a compatibility layer for Linux applications, though this approach revealed significant performance limitations for resource-intensive workloads. The browser application exhibited particular sensitivity to the virtualization overhead introduced by PRoot's userspace emulation. Enhanced performance required architectural changes involving root filesystem access through direct chroot operations, eliminating the PRoot translation layer for critical paths. This modification preserved the existing service management architecture while providing direct kernel interactions for latency-sensitive operations. The configuration maintained separation between application data storage and service deployment mechanisms, preserving rollback capabilities through versioned filesystem structures.

Accessibility requirements necessitated the implementation of cloud-based ingress solutions. Traditional public interface configurations were replaced by Cloudflare Tunnel architecture, which established outbound connectivity from the device to Cloudflare's network. This architecture provided geographic transparency through DNS-based service routing while maintaining operational consistency during network transitions. Remote browser implementation required additional complexity through tunneling of encrypted communication channels, maintaining inter-device synchronization through WebSocket encapsulation of TLS connections. Administrative access was secured through Tailscale's mesh networking capabilities, preserving direct connectivity while maintaining operational isolation from local network configurations.

The system architecture comprises layered responsibility assignments. The Android operating system maintains fundamental hardware interaction through its core kernel functions, while Termux provides the constrained Linux environment for service execution. Supervision layers including runit process management and Tailscale network integration operate within this constrained domain. The actual service implementations, including browser compositor and financial tracking systems, operate in isolated Linux environments with preserved root access. This architecture maintains clear boundaries between operating system responsibilities and application workloads while preserving the unique characteristics of mobile hardware.

The primary workload, the browser compositor service, represents the most performance-critical component. This implementation involves synchronizing touch input from one device with rendering operations on another through real-time media streaming. The infrastructure maintains multiple synchronization layers, including network round-trip compensation and protocol-level timing adjustments. The financial tracking system operates through a dedicated SQLite database with automated synchronization mechanisms, ensuring data persistence across device states. The deployment management system utilizes Ansible-based version control for both service definitions and runtime configurations, enabling reproducible recovery states through cryptographic verification.

The operational model presents several unique characteristics challenging traditional server paradigms. The shared kernel environment between Android and Linux applications introduces potential performance unpredictability. Security considerations require careful management of root access within a constrained trust boundary. The physical characteristics of the device necessitate specialized power management and thermal regulation strategies. However, these constraints are counterbalanced by advantages including form factor efficiency, built-in energy storage, and redundant connectivity options. The system demonstrates operational viability through its capacity for geographic mobility without configuration changes, maintaining persistent service availability across network transitions and physical relocations.

The implementation pathway represents a departure from conventional server deployment methodologies. The migration from VPS to mobile device required fundamental reevaluation of infrastructure assumptions. Key decisions included rejecting traditional Linux distributions in favor of hybrid operating system models, abandoning full-system virtualization approaches in preference for composited compatibility layers, and developing specialized deployment architectures for mobile-specific constraints. This development demonstrates that with careful architectural planning, traditional server functionalities can be effectively replicated in unconventional form factors while maintaining operational integrity and resource efficiency.
