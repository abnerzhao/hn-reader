## easy

Many people want to use two or more mice on one computer. Each mouse would show a different cursor on the screen. This can help with teamwork or games. I checked how well this works on Linux systems. The setup depends on parts working together. Some tools helped, but many needed more work. If you like this idea, we could work on it together!

The Wayland system, used in some Linux setups, has strong support for multiple mice. Its main rule lets devices be grouped into 'seats. ' Software like Weston and sway handle this well. Others, like niri, have no support yet. Programs like GTK or SDL work partly, but need fixes.

## medium

The idea of sharing a single computer with multiple input devices—each controlled by different people—has fascinated me. This concept, often called multi-seat, allows for collaborative use of a desktop environment without complex synchronization. While researching how this is handled on Linux and Wayland, I discovered both progress and gaps. The core wayland protocol supports multi-seat setups by linking input devices to seats, enabling independent cursor or keyboard controls. However, application support varies widely. Some tools work well together, while others ignore seat distinctions entirely. My investigation led me to create tools improving this functionality, though many challenges remain. Collaborative applications naturally benefit from multi-seat setups, as they let users interact directly through shared interfaces rather than relying on algorithms. This flexibility could transform how people work together in software, whether editing text or playing multiplayer games. The results are promising but require continued development.

Modern Wayland compositors and libraries show mixed support for multi-seat functionality. Weston, an early compositor, allows multiple cursors and per-seat window focus but trips up with edge cases like resizing conflicts. Sway, built on wlroots, offers robust features like dynamic seat assignment through terminal commands but has a bug where devices stack across seats. River, a modular compositor, natively handles seats but lacks a complete seat manager. Graphics libraries also differ: GTK4 passes seat information in events but neglects seat names, while SDL3 needs patches to track seats properly via mouse movement. Development tools like LÖVE, patched with SDL support, enable multi-cursor games where players control blocks collaboratively. Terminal emulators like Alacritty accept all seats’ inputs, but Kitty ignores extras. Applications remain scarce; I’ve built experimental prototypes like a text editor where cursors move independently, though features like text selection are missing. These examples highlight both potential and the fragmentation in current implementations.

Remote collaboration is possible through VNC setups like wayvnc, which creates virtual seats for each connecting user. This lets distant participants use their own cursor and keyboard within the same interface. Integrating such tools with browsers or native apps could enable shared editing or gaming across devices. However, challenges persist. Many applications assume a single input stream, dismissing seat data entirely. For instance, Firefox only acknowledges seats created at launch, while Chromium shows no reaction. Similarly, SDL’s absolute mouse mode discards seat information, requiring relative movement to work. Open projects aim to fix these gaps, such as improving cursor handling in browsers or enabling seat creation in KDE’s Kitty terminal. A key hurdle is ensuring consistency across layers: compositors, libraries, and applications must all respect seat data to avoid conflicts. Without standardization, multi-seat will remain a collection of workarounds rather than a seamless experience.

Despite progress, multi-seat on Wayland is incomplete. Core protocols provide a foundation, but compositors and libraries implement features unevenly. Some tools allow shared control, like multiple cursors editing a text document, but others fragment interactions. For example, closing a window with one cursor may hide another, or mice may unpredictably stack when reassigned. Applications are in early stages, with only prototypes like a GTK text widget or LÖVE physics game proving the concept. Remote VNC setups expand possibilities but lack polish. Many tools rely on unofficial patches or workarounds, indicating a need for broader adoption. The fragmentation means developers must piece together solutions, such as pairing a patched-LÖVE engine with a custom SDL setup. However, the underlying principle—collaborative input without complex logic—is compelling. As more tools adopt multi-seat, user experiences could shift from isolated applications to inherently cooperative environments. This would align with natural human interaction, where teams work side by side without competing over controls.

The future of multi-seat depends on community and developer effort. Open projects, marked with 📝, invite contributors to address gaps in seat management, especially in compositors like River or libraries needing seat-aware callbacks. Standardized protocols, like extending ext-transient-seat-v1 to River, could unify remote and local setups. For users, the promise is simpler collaboration: two people on one machine, each with their input device, working in the same interface without friction. Challenges remain, like making all applications seat-aware or resolving edge cases in user interface design. Yet, existing prototypes demonstrate potential. A browser that splits focus when users diverge, or a text editor where collaborators type in different sections, could become reality. While far from mainstream, multi-seat on Wayland remains an evolving space. Its success will hinge on solving technical mismatches and inspiring application developers to embrace this paradigm. For now, it’s a niche experiment—one that’s exciting to explore, especially with the right tools and support.

## hard

I began experimenting with attaching several mice to a single machine in order to obtain independent cursors on a shared desktop. Over three weeks of trial and error I evaluated the current state of multi‑seat support on Linux running the Wayland protocol. The outcome was unexpectedly robust: almost all layers of the stack, from the core protocol to the compositor, convey seat information to client applications, and several small utilities already provide most of the glue needed for a working experience. The work also uncovered a handful of gaps that remain open for future contributors.

While multi‑seat may seem esoteric, it offers practical benefits for real‑world scenarios such as pair programming, where one user can modify code in one window while another consults documentation in a sibling window. Games also benefit from having multiple independent pointers, mirroring the controller paradigm that many players are already familiar/business with. In all these cases collaboration is achieved without complex synchronization algorithms. Multiple cursors and keyboards controlled by distinct seats allow a natural form of coordination inside the shared desktop.

The Level of implementation varies across the stack. The base Wayland protocol itself is inherently seat‑aware, exposing each input event as a wl_pointer or wl_keyboard that is bound to a wl_seat and commonly emitting seat‑add or seat‑remove notifications. The reference compositor Weston delivers mandatory per‑seat window focus and simultaneous cursor motion, and five out of ten additional compositors support multi‑seat to varying degrees: sway, river, niri, GTK‑based clients and SDL devices each demonstrate حب distinct degrees of integration, while some, such as the niri compositor, still lack a general seat manager. Applications such as GNOME, Firefox and Alacritty have differing levels of seat awareness.

Clarity about terminology is essential. A logical seat groups input devices that belong to a single user sharing the function of the same desktop, producing distinct cursors and keyboard streams while operating the same window manager instance. Conversely, a physical seat refers to a complete independent workstation consisting of its own monitor, keyboard, and mouse paired with a single computer, which does not interact with other users within the same session. The post focuses on the logical seat model in which input devices are distributed across a shared desktop.

On Weston setting up multiple seats requires combining libinput with udev. Devices are identified by the device path obtained from `libinput list-devices`. The matching rules are written in `/run/udev/rules.d/00-multiseat.rules` with an environment variable `WL_SEAT`. For instance, a USB mouse can be bound to `second` while the keyboard receives the same seat name. After running `udevadm trigger` the device’s seat columnحاب shows `seat0,second`, signalling Weston's compositor that the two devices belong to the `second` logical seat. Reboot or a restart of libinput may be needed for the change to take effect.

With sway the process is programmatic. Listing inputs using `swaymsg -t get_inputs` and seats with `swaymsg -t get_seats` allows the administrator to assign devices rapidly via the `seat <name> assign <input>` command, creating the seat on demand. A notable bug is that reassigning a device does not replace its previous seat; instead it ends up in multiple seats, causing ambiguous pointer behaviour. The author has patched this issue and bundled a TUI tool called `multi-seat-configurator` that walks the user through assigning devices in an intuitive way.

On the application side, GTK4 exposes a `get_seat` hook for input events, enabling applications to branch logic according to the seat. Despite this, many widgets ignore seat changes after launch, a bug that must be repro'd and reported. The LÖVE 2D engine, built on SDL, can expose mouse `which` fields to Lua scripts by patching SDL. Terminal emulators are uneven: Alacritty accepts all seats, while Kitty only reacts to the first.
